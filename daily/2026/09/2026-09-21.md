# 2026-09-21 작업일지

## 오늘의 핵심

오늘은 기존 프로젝트 두 개를 실제 운영 구조에 더 가깝게 다듬고, 새로운 프로젝트 방향도 함께 정리했다.

- **Algo-Memory**: 로컬 전용 학습 도구에서 선택형 계정 동기화 구조로 확장
- **Re:Place**: 데이터베이스를 Supabase에서 Neon Postgres로 이전하고 검색/필터 UX를 SPA 방식으로 개선
- **프로젝트 기획**: 온체인 시그널 분석, 경제뉴스 자동 정리, 면접 대비 서비스 방향 구체화

## 1. Algo-Memory

### 진행한 작업

- 선택형 계정 동기화 기반 추가
- 이메일 인증 기반 계정 흐름과 Cloud Sync 연결
- Supabase 프로젝트 연결
- 계정 복구 흐름 보완
- Auth Modal 클릭/닫기 동작 수정
- OTP 인증 처리 수정
- 로그인 없이도 기존 로컬 사용 흐름을 유지
- 코드 채점 시 포매팅용 공백 차이는 오답으로 보지 않도록 수정
- 스타일 차이는 학습을 막지 않는 보조 피드백으로 분리
- 해당 동작에 대한 회귀 테스트 추가

### 오늘의 판단

기존 Algo-Memory는 로그인 없는 로컬 저장 방식이 단순하고 안전했지만,
여러 기기에서 학습 기록을 이어가려는 사용자를 위해서는 동기화 선택지가 필요했다.

그래서 로그인을 강제하지 않고,
**기본은 로컬 사용 / 필요할 때만 계정 동기화**하는 방향으로 잡았다.

또 코드 암기 서비스의 목적은 공백 위치를 외우는 것이 아니라 코드 구조와 논리를 기억하는 것이므로,
포매팅 차이를 오답으로 처리하지 않도록 채점 기준을 조정했다.

## 2. Re:Place

### 진행한 작업

- 데이터베이스를 **Supabase → Neon Postgres**로 이전
- 프론트엔드 조회를 Neon 기반 Postgres로 변경
- 크롤러 저장 로직도 Neon으로 이전
- Python Supabase Client를 psycopg 기반으로 교체
- JS Supabase Client를 pg 기반으로 교체
- GitHub Actions의 수집 환경도 Neon DATABASE_URL 기반으로 변경
- 연결 Pool을 Lazy Initialization하도록 수정
- SQL Parameter 형식과 Type 오류 수정
- 안전한 Database Health Check 추가
- 검색/필터 이동을 Client-side Navigation으로 변경
- 필터 동작을 새로고침형 페이지 이동보다 SPA에 가까운 경험으로 개선

### 오늘의 판단

프로젝트별로 Supabase 무료 프로젝트 수를 계속 늘리는 대신,
DB 용도로는 Neon을 사용해 서비스별 역할을 분리하는 방향으로 정리했다.

이전 과정에서 단순 연결 문자열만 바꾸는 것이 아니라
프론트 조회, Python 크롤러 저장, CI Secret, Connection Pool까지 전체 데이터 경로를 함께 바꿨다.

또 필터를 누를 때마다 페이지 전체가 다시 로드되는 경험이 서비스 사용성을 떨어뜨려
검색과 필터 조작을 Client-side Navigation으로 전환했다.

## 3. 신규 프로젝트 / 기획

### 온체인 시그널 분석

바이낸스 알트코인을 대상으로
온체인 지갑 움직임과 거래량, 급등 패턴을 함께 분석해
코인별로 서로 다른 시그널 전략을 적용하는 서비스 방향을 구체화했다.

핵심은 단순 대규모 이체 탐지가 아니라
재단 물량 해제, 스테이킹 해제 같은 정상 이벤트와
실제 세력성 자금 이동을 구분하는 것이다.

최종적으로는 웹에서 알트코인별 상태와 이상 지갑 이동을 실시간으로 확인하는 형태를 목표로 잡았다.

### 경제뉴스 자동 정리

기존 GONY DAILY / TechNews 구조를 참고해
경제뉴스를 하루 여러 차례 시장 시간대에 맞춰 분석하는 흐름을 설계했다.

예상 발행 시점은
새벽, 국내장 개장 전, 점심, 국내장 종료 후, 미국장 개장 전·후로 나누고
각 시점마다 단순 뉴스 수집이 아니라 시장에 미치는 의미까지 분석하는 방향으로 잡았다.

### 면접 대비 서비스

지원 직무의 예상 질문뿐 아니라
이력서와 실제 프로젝트 내용을 기반으로 개인화 질문을 만들고,
FM 답변을 반복 학습할 수 있는 방식에 대해 검토했다.

처음부터 별도 서비스를 만들기보다
기본 질문/답변 구조를 먼저 만들고 실제 면접 준비에 사용해본 뒤 서비스화 여부를 판단하는 방향이 적합하다고 봤다.

## 오늘 배운 점

1. **로그인은 기능이 아니라 선택지가 될 수 있다.**
   - Algo-Memory는 로컬 사용을 기본으로 유지하면서 필요한 사용자만 Cloud Sync를 사용하도록 구성했다.

2. **DB 이전은 Client 교체 하나로 끝나지 않는다.**
   - 조회, 쓰기, CI Secret, Connection Pool, SQL 문법까지 전체 흐름을 함께 확인해야 했다.

3. **정확한 채점과 지나치게 엄격한 채점은 다르다.**
   - 학습 목적과 무관한 포매팅 차이는 오답 판정에서 제외했다.

4. **새 프로젝트는 구현 전에 검증 질문부터 잡아야 한다.**
   - 온체인 프로젝트에서는 '대규모 이체가 실제 가격 움직임과 연결되는가'가 먼저 검증해야 할 핵심 질문이다.

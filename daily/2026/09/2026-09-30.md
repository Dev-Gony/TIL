## 1. Re:Place V2 기능 완성

체험단별 보상을 단순 금액 하나로 처리하지 않고 의미를 분리했다.

- 예상 현금
- 제공가치
- 포인트
- 환급
- 실제 현금 입금
- 실제 환급
- 입금일 / 환급일 / 메모
- 미정산 현금 / 환급 요약

제공가치와 포인트는 미정산 현금에 포함하지 않고,
null은 미입력 / 미확인 상태로 유지했다.

개인 정산 데이터는 사용자 소유권 기준으로만 생성·수정할 수 있도록 제한했다.

- 기존 Task 완료 처리 재사용

### RPL-022 — 개인 대시보드

/my 진입 즉시 우선순위를 파악할 수 있도록 정리했다.

## 2. 웹·앱 동기화 기반

### RPL-023 — Workspace 조회 API

향후 웹과 모바일이 같은 개인 데이터를 사용하도록
조회 계약을 하나로 통합했다.

- 공통 Workspace Contract
- 공통 Owner-scoped Loader
- GET /api/v1/me/workspace
- schemaVersion=1
- 구조화된 인증 오류
- /my SSR도 동일 Loader 사용
- 클라이언트 Reload를 Private API 4회 호출에서 Workspace Snapshot 1회 호출로 축소

### RPL-024 — Workspace Mutation API

조회 API에 이어 쓰기 경로도 v1 계약으로 통합했다.

- Favorites POST / DELETE
- Records POST / PATCH / DELETE
- Tasks POST / PATCH / DELETE
- Settlements PUT
- 구조화된 성공 / 오류 응답
- Mutation 후 Workspace Snapshot 재동기화

Owner ID는 Client가 보내는 값을 신뢰하지 않고 서버 Session에서만 파생하도록 유지했다.

## 4. Vercel Build 전략 변경

오늘 중요한 개발 프로세스 변경도 있었다.

작은 변경마다 Branch Push → Vercel Preview Build가 반복되면서
Build Rate Limit과 불필요한 대기 문제가 발생했다.

앞으로는 기능 단위로 작업을 묶는다.

- 중간 Push 최소화
- 코드 / 테스트 / 문서를 먼저 하나의 기능 단위로 완성
- 여러 파일을 한 Batch로 정리
- Branch Ref는 가능한 한 한 번만 갱신
- 기능당 Preview Build 기본 1회
- 큰 기능 또는 마감 검증 시점에만 Build

이 정책을 AGENTS.md와 MODEL_EXECUTION_PLAN.md에도 기록했다.

### 핵심 판단

CI / Preview는 안전장치이지
파일 하나 수정할 때마다 무조건 실행해야 하는 의식이 아니다.

**작은 변경마다 Build하는 대신 검증 가능한 기능 단위로 묶어 Build한다.**

## 6. V3 시작 — 블로그 분석

V2 종료 직후 V3 첫 기능으로 넘어갔다.

### RPL-028 — 블로그 분석 지표·근거 데이터 기반

블로그 분석을 출처 불명 점수나 임의 등급으로 만들지 않고,
근거 데이터를 설명할 수 있는 구조부터 만들었다.

#### 5개 Dimension

- Activity
- Visibility
- Consistency
- Audience
- Content

#### 분석 구조

- 0~100 자체 Score
- Coverage
- Confidence
- 내부 Band
  - START
  - GROW
  - STABLE
  - STRONG
- Signal별 Source / ObservedAt / Available
- Missing Dimension은 0점 처리하지 않고 계산 분모에서 제외
- 과거 Legacy Grade는 Reference-only

### 핵심 판단

블로그 분석에서 중요한 것은 숫자를 보여주는 것이 아니라
**어떤 데이터로 왜 이 점수가 나왔는지 설명할 수 있는가**였다.

## 7. RPL-029 — 네이버 블로그 RSS Live-data Adapter

RPL-028 분석 엔진에
실제 네이버 블로그 공개 RSS 데이터를 연결했다.

### 구현

- 고정 RSS Origin: https://rss.blog.naver.com/{blogId}.xml
- Normalized Blog ID로 Server에서 URL 조립
- 임의 URL Fetch 금지
- 5초 Timeout
- 1 MiB Response Limit
- 최근 Evidence 최대 10건
- 최근 30일 발행 수
- 마지막 발행 경과일
- Category Coverage가 충분하면 Topic Concentration 계산
- POST /api/v1/blog-analysis/preview
- RSS Fixture 기반 Runtime Test

### 의도적인 미구현

현재 RSS에서 알 수 없는 값은 억지로 추정하지 않았다.

- 검색 노출
- 독자 반응
- 콘텐츠 충실도

이 Dimension들은 unavailable로 유지했다.

### 핵심 판단

없는 데이터를 0점으로 만드는 것보다
**모른다는 사실을 데이터 계약에 그대로 표현하는 것이 신뢰도 높은 분석**이다.

## 8. 오늘 배운 점

1. **로드맵 단계는 기능 개수로 끝내지 말고 사용자 Journey로 종료 검증해야 한다.**
   - V2는 RPL-027 E2E Closeout을 기준으로 종료했다.

2. **웹·앱 동기화는 UI보다 데이터 계약을 먼저 통일해야 한다.**
   - Workspace Read / Mutation API를 Versioned Contract로 묶었다.

3. **Offline 기능을 추가할수록 Privacy Boundary가 더 중요해진다.**
   - 개인 Workspace 데이터는 Service Worker Cache 대상에서 제외했다.

4. **Build도 자원이다.**
   - 작은 Push마다 Preview를 돌리는 방식에서 기능 단위 Build Budget 방식으로 변경했다.

5. **분석 서비스는 모르는 값을 아는 척하지 않아야 한다.**
   - Missing Signal을 0점으로 처리하지 않고 Coverage / Confidence에 반영한다.

6. **V3는 블로그 지수 숫자 하나보다 설명 가능한 근거 데이터부터 시작해야 한다.**

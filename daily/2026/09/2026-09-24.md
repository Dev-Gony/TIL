## 3. Algo-Memory

### Supabase → Neon 전환

비용과 인프라 수를 줄이기 위해 Algo-Memory의 선택형 Cloud Sync를
Supabase 중심 구조에서 Neon으로 옮기는 작업을 진행했다.

### 진행한 작업

- Supabase → Neon Migration을 위한 Reversible Path 준비
- Neon Auth의 Text User ID 기준으로 RLS 수정
- Supabase를 기본으로 유지한 Neon Shadow Mode 추가
- Shadow 검증 후 **기본 Cloud Backend를 Neon으로 Cutover**
- Supabase는 명시적인 Rollback Mode로 유지
- Production Deployment Config 정리
- Python / SQL Curriculum 설명 오류 수정
- SQL 복습 문제에 실제 Table Schema Context 제공
- Curriculum Content Quality Eval 추가
- Content Eval을 npm test / Deploy CI Gate에 포함

### 오늘의 판단

인프라 이전은 한 번에 Provider를 갈아치우는 방식보다

**준비 → Shadow Mode → RLS 검증 → Default Cutover → Rollback 유지**

순서로 진행하는 편이 안전했다.

또 학습 서비스의 코드가 정상 동작해도
잘못된 문제 설명이나 SQL Schema가 배포되면 학습 품질 자체가 깨지므로,
콘텐츠 품질도 CI에서 검증하도록 범위를 넓혔다.

## 오늘 배운 점

1. **기능 확장과 검증 완료는 별개의 상태다.**
   - Prism에서 기능을 대량 확장한 뒤 Golden Validation / Regression / CI Gate를 별도 단계로 추가했다.

2. **인프라 이전은 단계적으로 해야 Rollback이 가능하다.**
   - Algo-Memory에서 Shadow Mode를 거친 뒤 Neon을 기본값으로 전환했다.

3. **서버리스 DB 비용은 Provider보다 Connection 사용 방식의 영향도 크다.**
   - Re:Place에서 Pool 재사용과 Read Cache를 함께 적용했다.

4. **게임 프로토타입도 자동 검증할 수 있다.**
   - AFFIX: ZERO의 핵심 전투·진행·루팅 루프를 Godot Headless Smoke Test로 검증하도록 구성했다.

5. **README와 Portfolio도 실제 구현 상태를 계속 따라가야 한다.**
   - 코드와 문서가 벌어지기 시작하면 프로젝트 설명 자체가 신뢰를 잃는다.

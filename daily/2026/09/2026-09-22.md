## 2. Algo-Memory

### 진행한 작업

- 받아쓰기에서 Tab 입력을 코드 들여쓰기로 사용할 수 있도록 개선
- 학습 완료 후 실제 실행 결과 예시를 바로 확인할 수 있도록 추가
- Python / SQL 템플릿에 대표 실행 결과를 확장
- 예약 복습을 완전 백지 방식에서 회상 단서 기반 복습으로 변경
- 복습 문제를 모호한 힌트가 아니라 명시적으로 채점 가능한 문제 문장으로 개선
- Reference Code의 실제 식과 식별자에서 복습 요구사항을 생성하도록 수정
- Dashboard의 신규 학습 개수를 실제 할 일 수와 일치하도록 수정
- 관련 회귀 테스트 추가

### 오늘의 판단

복습 단계에서 아무 설명 없이 처음부터 백지 코드를 요구하면
기억을 강화하는 과정이 아니라 단순 실패 확인에 가까워질 수 있다고 봤다.

그래서 **복습에서는 핵심 개념과 명시적 요구사항을 제공하고,
최종 실전/백지 재현은 별도로 유지**하는 구조로 분리했다.

또 결과를 실행해서 확인할 수 있게 만들어
'코드를 외웠는가'뿐 아니라 '이 코드가 실제로 무엇을 만드는가'까지 연결했다.

## 3. On-chain Signal

### 오늘 구체화한 내용

- Codex Astro + high 기준으로 개발할 상세 PRD 작성
- 단순 실시간 알림 서비스가 아니라 **과거 단일 코인 분석 → 백테스트 → 실시간 전진 검증** 순서로 개발 기준 확정
- 특정 알트코인의 과거 지갑 이동을 당시 정보 기준으로 재현하는 기능을 핵심 범위에 포함
- 사후 해석과 당시 시점 예측 재현을 분리
- 데이터 누수 방지 기준을 별도 테스트 대상으로 지정
- 서브에이전트 역할, Harness, Eval, Acceptance Test를 PRD에 포함
- 신호 중복, 상장폐지, 데이터 결측 등 현실적인 실패 케이스를 수용 테스트에 포함
- 검증 전에는 상승 확률을 임의로 표시하지 않는 원칙 설정

### 오늘의 판단

온체인 데이터가 많다는 이유만으로 예측 서비스가 되는 것은 아니다.

먼저 **과거 급등 전에 실제로 유의미한 지갑 이동 신호가 반복됐는지**를 검증해야 하므로,
실시간 대시보드보다 Historical Replay와 Backtest를 우선하는 순서로 확정했다.

## 오늘 배운 점

1. **Toy 프로젝트도 통합 검증까지 가야 실제 경험이 된다.**
   - 코드 작성과 Unit Test에서 끝내지 않고 PostgreSQL, Redis, pgvector, MCP를 실제 실행 경로로 검증했다.

2. **복습과 실전은 같은 UX일 필요가 없다.**
   - 복습은 회상 단서를 제공하고, 최종 실전만 백지 재현으로 유지하는 편이 학습 목적에 맞았다.

3. **예측형 프로젝트는 화면보다 검증 설계가 먼저다.**
   - On-chain Signal은 Backtest와 데이터 누수 방지 기준을 먼저 고정했다.

4. **Harness와 Eval은 문서 장식이 아니라 구현 진척을 판단하는 기준이어야 한다.**
   - NoticeGuard와 On-chain Signal 모두 기능 목록보다 검증 가능한 완료 조건을 먼저 명확히 했다.
